# DEBUG журнал прикладных сценариев

## Включение

Laravel берёт канал из `LOG_CHANNEL` (по умолчанию `stack` → `single`) и минимальный уровень из `LOG_LEVEL` (по умолчанию `debug` в `config/logging.php`). Канал `single` пишет в `storage/logs/laravel.log`; `daily` хранит файлы 14 дней. Настраивайте уровень в локальном окружении без публикации значений `.env`. После изменения конфигурации с кэшем конфигурации нужно обновить кэш обычным способом проекта.

В PowerShell последние записи удобно читать так:

```powershell
Get-Content .\storage\logs\laravel.log -Tail 100
```

Для одного сценария:

```powershell
Select-String -Path .\storage\logs\laravel.log -Pattern 'chat.message.send|chat.message.broadcast'
```

## Структура записей

- `DEBUG`: выбранный сценарий, этап, число обработанных сущностей, направление страницы и источник настроек. Запись помогает восстановить ход операции и не означает её успех.
- `INFO`: завершённое изменение или постановка результата в очередь доставки. Для broadcast окончательное подтверждение относится к отдельной записи отправки адресату.
- `WARNING`: ожидаемый отказ или неполный справочник, например отсутствующий связанный пользователь, категория или вложение.
- `ERROR`: этап сбоя, класс исключения и безопасные идентификаторы. Исходное исключение передаётся вызывающему коду; текст исключения не записывается в структурированный контекст.

Сообщение задаётся постоянным ключом вида `домен.сценарий.событие`; контекст передаётся вторым аргументом `Log::debug/info/warning/error`. На границе запроса используются `actor_id`, `user_id`, `deal_id`, `chat_id`, `task_id`, `report_id`, `funnel_id` и `media_id`, когда они известны. Для коллекции пишется `*_count`, для выбора варианта — `type`, `source`, `direction` или `step`. Пустой ID означает, что вызов не имел HTTP пользователя; отправитель фонового сообщения определяется по `chat_messages.user_id`.

## Сценарии

| Сценарий | DEBUG и диагностический смысл | Завершение и отказ |
| --- | --- | --- |
| Документы | Подготовка шаблона, конвертация и сохранение Media отмечаются по ID сделки и этапу. | INFO для готового документа; ERROR с этапом отказа и очисткой созданного Media. |
| Диск | Решения по пути, коллизии имени и переход корзины отмечаются по ID и хешу пути. | INFO для завершённого перемещения; WARNING для коллизии; ERROR при отказе Storage или БД. |
| Чаты | `chat.setup.scenario` показывает ветку `staff`, `partner` или `client`; `chat.categories.initialized` содержит `mapping_count`; `chat.message.list.loaded` содержит `direction` и `message_count`. | `chat.setup.completed`, `chat.message.send.completed`, `chat.message.broadcast.sent`; соответствующие `*.failed` указывают этап и ID без текста сообщения. |
| Задачи и поля | `task.create.scenario_selected` фиксирует тип; `user_field.values.saved` и `role.field_access.synced` показывают число обработанных полей. | `task.notification.failed` и `user_field.attachments.add.failed` фиксируют сбой без значения поля или имени вложения. |
| Отчёты и секции | `report.filter.applied` содержит `filter_count`; `report.fields.loaded` и `report.export.rows_prepared` показывают число видимых полей и строк; `section.source.selected` различает `personal` и `default`. | `report.export.completed` подтверждает запись файла; `report.export.write_failed` и `section.values.failed` указывают ID и этап. |
| Пользователи и база знаний | `table_settings.source_selected` содержит `source` и `template_id`; `knowledge_base.contents.created/updated` — число элементов. | `user.provision.completed`, `auth.avatar.changed`; при отказе фиксируется класс исключения без учётных данных и содержимого. |

DEBUG запись о начале операции не является свидетельством commit: ориентируйтесь на запись завершения и состояние БД. Broadcast и уведомления могут выполняться после commit; их отказ не отменяет уже зафиксированную запись. При откате транзакции запись о завершённой внешней доставке появляться не должна.

## Ограничения данных

Не помещайте в журнал текст сообщений, документы, значения пользовательских полей, адреса электронной почты, пароли, токены, коды восстановления, полные пути файлов, содержимое XLSX или бинарные данные. Для диагностики коллизий пути используйте хеш пути. Счётчики и идентификаторы достаточны для сопоставления с записью в БД. Новые DEBUG записи добавляйте на значимые границы сценария и шагов, не на каждое чтение модели или итерацию коллекции.
